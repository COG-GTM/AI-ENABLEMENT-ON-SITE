What MCP is, without the jargon

  • An MCP server is a small program that hands Devin extra tools: read a requirement, query the tracker, look inside a file
  • It answers three messages and nothing else: who are you, what tools do you have, run this tool
  • Devin either starts that program on your machine, or connects to one someone else hosts over HTTPS
  • The tools then appear in every session, named and described, instead of being re-explained each time
  • Hosting is only the question of where the program runs and who looks after it

What changes for the people doing the work

Without MCP

  • Every session starts by explaining the API again
  • Exports get pasted in by hand, or not at all
  • Each engineer improvises their own credential handling
  • No shared definition of what Devin is allowed to read

With MCP

  • The tools are present at session start, already described
  • Each tool declares its inputs; bad arguments are refused
  • Credentials stay in the shell as placeholders, never in chat
  • One reviewed config entry the whole team clones

Models A and B: run it on the laptop

For

  • Nothing leaves the machine; works with no network at all
  • No approval needed: it reads only what you can already read
  • Already set up here, one entry and one command
  • B adds a single reviewed entry that every clone inherits

Against

  • Every laptop needs the runtime installed and kept current
  • No central record of who asked what
  • One credential per person to issue, rotate, and revoke
  • The server holds your permissions, so keep it read-only

Model C: hosted by your platform team

For

  • One server, many laptops; nothing installed per machine
  • One audit log: tool, caller, time, outcome
  • One place to rotate or revoke a credential
  • Access controlled at the network and at the proxy

Against

  • A real service to build, run, patch, and page on
  • A down host now stops everyone, not one person
  • Needs a TLS certificate the laptops already trust
  • Change control before the first user connects
  • Nothing in this repository stands one up for you

Model D: hosted by the vendor

For

  • Nothing to host; the vendor runs and updates it
  • Browser sign-in gives per-user identity and expiry
  • Fastest path when the vendor already offers an endpoint

Against

  • Requests leave your network for the vendor's cloud
  • A vendor outage or an expired token stops the tools
  • Needs administrator approval before the first connection
  • Do not assume it sits inside your authorization boundary

Where the entry lives, and where the secret does not

  • Project file, checked in: the entry everyone who clones the repository should get
  • Local override, never checked in: your personal token, or something you are trying out
  • User file on your machine: servers you want in every project
  • Secrets are written as a placeholder that reads your shell or a file, never as the value
  • An override with the same name must repeat every key of the entry it replaces
  • A newly added server needs a new session; the list is read at startup

What the readiness check enforces for you

  • Every entry in all three config files is validated, not just the one you edited
  • A remote server must use HTTPS, and a known transport
  • A local server's command must actually exist on this machine
  • Anything that looks like a pasted token is rejected outright
  • The wrong placeholder syntax is flagged before it silently becomes empty
  • An override that quietly drops a field fails the check

What this repository has not proven

  • Model A is the only one tested end to end here
  • No hosted HTTP server, reverse proxy, or certificate is set up by this repository
  • No browser sign-in flow and no vendor endpoint has been exercised
  • Nothing here has been run inside a customer network or against a live tracker
  • File locations and CLI commands come from the product documentation; confirm them against your build
  • No vendor service is inside your authorization boundary by default
