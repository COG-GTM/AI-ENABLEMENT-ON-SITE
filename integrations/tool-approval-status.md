# Tool approval status (FedRAMP and agency software approval)

A single table a site administrator can walk through before the first demonstration: every tool,
install, download, package, CLI, service, and vendor product that this repository recommends,
lists as optional, or plans to add, with what the FedRAMP Marketplace said about it on the date
checked. Nothing here is a boundary claim; it is the evidence the administrator needs to make one.

## What FedRAMP covers, and what it does not

FedRAMP is the U.S. Government program for authorizing **cloud service offerings** (SaaS, PaaS,
IaaS) for federal use. The [FedRAMP Marketplace](https://www.fedramp.gov/marketplace/) is the
official, searchable record of those offerings, their impact level (LI-SaaS, Low, Moderate, High),
their authorizing path, and their status. The Marketplace
[quick start guide](https://www.fedramp.gov/marketplace/guide) tells agency users to first
"ensure that your use case falls within the scope of FedRAMP". The Marketplace currently labels a
completed authorization **"FedRAMP Certified"**; this document keeps the shorter word
**Authorized** in the status column and records the Marketplace label verbatim in the evidence column.

FedRAMP does **not** authorize desktop software, on-premises servers, operating-system features,
compilers, open-source libraries, or Python wheels. Those fall under the agency's own
software-approval process (an approved-products list, a change board, or whatever the site uses).
In the table they are marked **Not applicable**, which means "not a FedRAMP question; ask the
administrator's software-approval process instead". It never means "approved".

Two repository rules govern how this table may be used (`AGENTS.md`, `SECURITY.md`):

- "Do not claim a service is inside a FedRAMP boundary unless the user's administrator confirmed it."
- Prohibited content includes "unverified claims that a service or integration is FedRAMP authorized".

A Marketplace listing says a cloud service **has** an authorization. It does not say **your**
deployment of that service is inside **your** authorization boundary. Only the site administrator
(or the agency's authorizing official) can say that.

## How to use this table with a site administrator

1. Print or open this file together. Work down the **Status** column.
2. **Authorized / In Process** rows: hand the administrator the package id and the Marketplace
   link. Ask one question: "Is this offering, at this impact level, inside our boundary and approved
   for the data we will show?" Record the answer; do not infer it.
3. **Not on Marketplace** rows: the service exists but has no FedRAMP listing. Either the
   administrator approves it through another route, or the repository's offline path is used
   instead. Every network-dependent item here has an offline alternative noted in the last column.
4. **Not applicable** rows: FedRAMP is not the question. Ask whether the software is on the site's
   approved list; if not, the repository still runs without it (see the closing section).
5. **Unknown** rows: evidence was missing on the date checked. Treat as "not approved" until the
   administrator resolves it. The reason for the unknown is in the evidence column.
6. Re-check dates: Marketplace status changes. Anything older than the site's re-verification
   window should be looked up again at <https://www.fedramp.gov/marketplace/products/>.

Categories used below: **cloud service**, **desktop or on-prem software**, **open-source
library**, **vendor commercial product**, **operating-system feature**. Date checked for every
Marketplace lookup: **2026-09-29**, against the prerendered product list served at
<https://www.fedramp.gov/marketplace/products/> (the legacy `marketplace.fedramp.gov` host now
redirects there).

## What the repository itself requires

The base path is **Python 3.10+ and its standard library, offline, no service**. `tools/doctor.py`
checks exactly that and reports READY without any of the optional items above; its docstring says "Never touches the network. Standard library only.". Everything else in the table is optional and degrades gracefully: without a C
compiler and `make`, `tools/doctor.py` prints SKIP and the Python firmware twin runs the same
tests; without `lvkit`, `tools/vi_fleet_scan.py` inventories by filename and `/labview-to-python`
works from exported VI documentation; without `cppcheck`, `/bring-your-firmware` still maps and
tests logic; without Docker, the Jira connector has a Python form; without any approved external
service, lanes 2-4 in `integrations/README.md` are replaced by lane 1, the offline fake server and
the local reference MCP server. A site administrator who approves nothing beyond Python and this
folder still gets every Python tool in `tools/` and `integrations/`; running the skills in `AGENTS.md`
themselves additionally needs Devin Desktop (see that row), which is the one item the base path
cannot remove.
