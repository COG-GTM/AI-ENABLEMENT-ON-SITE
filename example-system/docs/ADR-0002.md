# ADR-0002: UART uplink for the first build, CAN kept as an option

- Status: Accepted
- Date: synthetic
- Relates to: SN-REQ-004, SN-REQ-005, SN-REQ-020, ICD section 4

## Context

The node must deliver one 16-byte packet per second to a host. Candidate links were UART
(115200 8N1) and CAN 2.0B (500 kbit/s). Only one node exists in the first build; a multi-node
bus is a possible future need (tracked as SN-CAP-002).

## Decision

Ship UART now. Keep the packet format bus-agnostic (fixed 16 bytes, own CRC) so a CAN transport
can carry the same payload in two frames without changing `packet.c`.

## Alternatives considered

| Option | Pros | Cons |
| --- | --- | --- |
| UART (chosen) | Zero extra parts, ~0.2 mA average, host tooling everywhere | Point-to-point only, no arbitration |
| CAN 2.0B | Multi-node, robust arbitration, built-in CRC | Transceiver adds ~5 mA active current and a part; 8-byte frames need fragmentation |
| I2C to a gateway | Reuses existing bus | Gateway becomes single point of failure; bus already used by the temperature sensor |

## Consequences

- Power budget assumes UART (`POWER-BUDGET.md`); a CAN swap must re-run the budget (`/what-if-part-swap`).
- The packet keeps its own CRC even though CAN has one, so the format stays transport-independent.
