# Fallback Plan

Every primary scenario must have a fallback that demonstrates the same learning objective without requiring broader access.

| Failure | First response | Fallback |
| --- | --- | --- |
| Authentication unavailable | Stop login attempts and notify the approved support role | Walk through sanitized screenshots or a recorded local sequence |
| Network blocked | Keep the block in place | Use local documentation and preinstalled dependencies |
| Integration unavailable | Disable or decline the tool | Use a synthetic local issue, log, or API fixture |
| Build dependency unavailable | Do not install from an unapproved source | Use a prebuilt fixture or documentation-only scenario |
| Agent output is incorrect | Show the review failure honestly | Ask for correction, compare with expected evidence, or use prepared diff |
| Write access unavailable | Keep repository read-only | Run code-understanding, review, or planning scenario |
| Performance is poor | Stop repeated retries | Use a prepared transcript with the same review points |
| Sensitive content appears | Stop sharing and follow the approved incident process | Resume only with a clean synthetic workspace after clearance |

## Fallback asset rules

Fallback screenshots, recordings, transcripts, diffs, and logs must be sanitized, approved, and stored without identifying metadata.
