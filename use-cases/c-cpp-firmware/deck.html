Three kinds of code in every firmware tree

  • Portable logic: parsers, filters, checksums, state machines - testable on a laptop
  • Target-only: ISRs, memory-mapped registers, startup, linker sections, inline assembly
  • Vendor and HAL: code you did not write and should wrap, not port
  • Before modernising anything: which is which, where the HAL seam is, what depends on what
  • A Python model, where wanted, is a behavioural twin proven against the C - not a translation

Classification and seams

How a file is classified

  • retain: ISR, inline asm, memory-mapped registers, linker symbols or sections, startup code
  • wrap: vendor / third-party, HAL-bound, includes a target-only header
  • port: host-testable logic
  • unreadable: could not be read or parsed - listed, not dropped

Seam candidate

  • A function in a retain / wrap file that host-side code calls
  • That is where the stub goes in templates/host-harness
  • gcc -MM cross-checks includes when gcc exists; its errors are reported verbatim
  • Without board flags the fixture reports: error: #error "unknown board"

What this does not prove

  • Macros not expanded, #if not evaluated, function pointers not followed: edges are candidate evidence
  • C++ overloads, templates, virtual dispatch are matched by name only
  • Host tests prove logic on a laptop, not timing or interrupt behaviour on the target
  • No C-to-Python translator exists here; if translation is the requirement, say it is a gap
