One script is easy; the repository is the problem

  • Hundreds or thousands of .m files: scripts, functions, +packages, @classes, private/ folders
  • The cost is in interconnections: who calls what, through which path, and what is dynamic
  • Toolbox calls and shadowed built-ins decide what can leave MATLAB at all
  • Goal: document the repository and migrate it without feeding the whole codebase to an agent each step
  • No MATLAB licence needed for discovery; vectors from the original are needed for proof

How names are resolved

In MATLAB's order, as far as text allows

  • local function -> private/ -> function in tree -> frozen core list -> frozen toolbox lists
  • +package and @class membership from the folder, classdef methods from the file
  • Duplicates are marked ambiguous, never guessed
  • Shadowed built-ins and workspace inputs are reported per file

What stays unknown, and is said so

  • eval / evalin / feval / str2func / cellfun targets: listed as dynamic
  • Path order and runtime dispatch
  • Which toolboxes are actually installed
  • Numeric behaviour: only vectors + bench_compare.py prove that

Bounded packs instead of the whole repository

  • One Markdown pack per backlog unit: source, direct dependencies, callers, open questions, boundaries
  • Budget per pack (default 8000 tokens est.); dependencies are trimmed before source, truncation is marked
  • Manifest records bytes and estimated tokens per pack so token use is visible before any agent runs
  • Each pack ends with a result contract: id, status, target, evidence files, blocked_on
  • Leaf-first order: dependencies migrate before their callers
