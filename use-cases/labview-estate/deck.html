The problem is dependencies and built-ins, not syntax

  • Thousands of binary .vi files, .lvproj projects with RT / FPGA targets, TestStand .seq callers
  • Translating one VI at a time loses what calls what and what belongs to which target
  • LabVIEW built-ins (vi.lib, DAQmx, FPGA primitives) have no one-line equivalent
  • Needed: extraction -> project-level dependency map and description -> migration plan -> proof
  • Target language stays selectable after decomposition (Python, C#, C++, keep in LabVIEW)

Extraction: what the JSON holds

lvkit describe / unresolved, per file

  • Block-diagram nodes with uids, wires as nets, connector pane, library and class facts
  • Unresolved primitives and terminal mappings, by name
  • Per-file calls: one unreadable VI never stops the scan
  • lvkit index + query add callers and impact when a tree index succeeds

Why not PyLabVIEW

  • PyLabVIEW dumps RSRC resource blocks to XML
  • No diagram semantics (nodes, wires, connector) come out of it
  • Fine as a second extractor; not sufficient alone
  • See integrations/lvkit.md for the offline wheel install

Classification with reasons, priority from evidence

  • retain: FPGA, Real-Time, DAQmx hardware timing, target-only I/O
  • wrap: proprietary drivers, instrument libraries, anything behind a vendor boundary
  • port: sequencing, math, parsing, file and report logic
  • unreadable: lvkit absent or the file failed to parse; the reason is recorded
  • Priority = impact (callers, sequence references) x readiness (recording present, no unresolved built-ins)
  • Rescans merge into the existing backlog: ids and hand-set statuses survive

What this does not prove

  • The graph is static: dynamic calls (VI Server, Call By Reference) appear as unresolved
  • port / wrap / retain are classifications with reasons, not decisions
  • Hardware timing, FPGA, and RT determinism stay on the target; the map shows the boundary
  • The whole estate is never sent to an agent: one pack per VI, budget per pack
